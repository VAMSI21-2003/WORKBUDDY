# OWASP ASVS level 1: the backend

What this is: a read of the backend (`backend/`, the parts of `skills/` and `buddy/` that open an uploaded file, `deploy/Caddyfile`, the `Dockerfile`) against the requirements of OWASP ASVS 4.0.3 level 1, one verdict each, with the evidence. It is a self-review by the session that wrote the change, then a fresh reviewer's check (`docs/reviews/fix-security-pass-review.md`). It is not a penetration test and not a certification.

**Verdicts.** Pass: the requirement holds and the evidence shows it. Fail: it doesn't hold; the severity is in brackets. N/A: the application has no such feature. Where a verdict rests on a deployment fact I could not run here (Caddy, Docker, a real Let's Encrypt certificate), it says so.

**Method.** Read the code named in each row. Ran the real app on production settings against the fake identity provider (`tests/idp`) and probed it. Every probe that is a guard is now a test, in `tests/backend/test_asvs_l1.py` (the cookie flags, the headers on every kind of response, CSRF, another person's session on every route that names one, the sign-in redirect, file names, error bodies, guessing, the routes that must not exist). Line numbers are for the commit this file was committed with; the function names are the stable part.

**Result.** One Fail rated MEDIUM, found and fixed on this branch: SQL built from a column header (V5.3.4, row 5.3.4 below). Four Fails rated LOW, not fixed, with the reason each time (14.4.5, 14.4.2, 12.4.2, 5.1.1). No Fail rated HIGH. Every other L1 row that applies to this backend is a Pass.

## V2 Authentication

People sign in with Google (OpenID Connect, authorization code with PKCE). The application stores no password. Scripts use an operator token; the demo password exists outside production only (`backend/settings.py` `_check_access`: in production the demo password is ignored and a missing Google client refuses to start).

| 5.3.4, 5.3.5 injection into queries | **Fail (MEDIUM), fixed** | `skills/excel/analyze.py` `NearDuplicateAnalyzer` built Splink/DuckDB SQL from the uploaded sheet's column headers (`block_on(f"substr({name_column}, 1, 3)")`, `cl.NameComparison(name_column)`). [Possible] that a crafted header that parses can run DuckDB functions on the server (`read_text`, `read_csv`); I did not build one. | 5.3.8 OS command injection | Pass | No subprocess anywhere in the application (5.2.4). |
| 5.3.9 local and remote file inclusion | Pass | A file is opened only by a path the server built from its own ids (rows 12.3.x). |
| 5.3.10 XML injection and XXE in uploaded workbooks | Pass (before and after) | An `.xlsx` is XML in a zip. In the production image openpyxl runs on the standard library parser (`defusedxml` and `lxml` are not in `requirements-runtime.lock`); measured on the pre-fix code with both switched off: an external entity is `undefined entity` (no file read) and a billion-laughs sheet stops at expat's amplification limit in 0.18 s. Added on this branch, as defence in depth and a clearer refusal: every XML part is read with a parser and any DOCTYPE or ENTITY declaration refuses the workbook (`skills/excel/workbook.py` `check_workbook_limits` and `_declares_entities`, which refuse on the parser's DOCTYPE and entity events in every part; fixed text). Tests: `tests/skills/excel/test_hostile_workbooks.py` (entity expansion in five part types, a declaration behind a 6,000-byte comment, UTF-16, an external entity). |
| Decompression bomb, huge sheets, huge strings (feeds 12.1.1, 12.1.2) | Pass for what is measured here; the limits are unmeasured in the production image until the owner runs `scripts/measure_workbook_check.py` there (fixed on this branch, after review rounds 1 to 4) | A 2 MiB `.xlsx` can unpack to gigabytes; a 1.5 KB one can make a reader build tens of millions of cells; a 22 KB one can point a thousand cells at one huge string; a 160 KB one can hold a million relationships that openpyxl parses whole on every load. Four rounds in a row found a way past a list of caps (counted XML elements, then the rows by my own parser, then caps by part name, which openpyxl doesn't use to find parts), so the list was replaced by a resource limit. `check_workbook_limits` (in `sheet_names()`, which the planner, both cleaning skills and the Inspector call first, and in the analysis skill and the Inspector's other reads) does the cheap checks in the server instantly: more than 1,000 parts, more than 64 MiB unpacked by the directory (`zipfile` never hands over more of a part than its directory declares), any DOCTYPE or entity declaration in any part, and a `[Content_Types].xml` over 16 MiB (as on `main`). Then it runs the readers the app uses on the file in a **child process** (`_scan_in_child`): the row-by-row walk that counts what the table would be built from (200,000 rows over all sheets together, 1,000 columns, 1,000,000 cells, 32,767 characters in a cell, 4 million bytes of text as CPython stores it: 1, 2 or 4 a character), `sheet_names`, and the two reads the analysis holds at once (`pd.read_excel` default and `dtype=object`). The child has an address-space cap of 512 MiB and 60 s, sets its own `oom_score_adj` to 1000 so a container that runs out of memory kills it, not the server, and takes one at a time (a second check waits 10 s, then the turn says the server is busy; that is not kept as a verdict). A memory error, a timeout, a crash, no answer or an answer the parent doesn't know is a refusal, never a pass, and every message is fixed text (the child answers with a number the parent maps to a sentence; nothing from the file or the child is shown). What the child read inside its limits bounds what the server's own later reads need, because they are the same reads, so no list of parts is needed. Not covered by the child: the layout check and the formula count (they stream rows over the same load and add time, not memory) and the memory of the analysis itself (ydata-profiling and Splink on the table; bounded by the cell cap, the 100-character and pair limits in `skills/excel/analyze.py`). On a platform without `resource` (Windows) only the time limit applies. Tests: `tests/skills/excel/test_scan_child.py` (see fixes4: the round 4 bombs, P1, P4 and P7b, refused by what they need; the child's reads, limits, time, crash, unknown answers, OOM score, one at a time, busy), `tests/skills/excel/test_hostile_workbooks.py` (the counters, on real workbooks the reader opens; their limit changes now reach the child), `tests/skills/excel/test_analyze.py` for the near-duplicate bounds. Measured on this sandbox with the standard-library parsers (the image has no lxml), 512 MiB and 60 s: all of the reviewer's bomb files (P1 to P8c, P10, M1 to M4, M6 long names, M7, M8) refused, in 0 to 60 s with the child at 410 to 415 MiB resident; ordinary and at-cap files passed, among them 1,000,000 numeric cells in 39 s with the child at 133 MiB. **Those figures are this sandbox's, not the image's.** |

## What this did not cover

- Levels 2 and 3, and the L1 items that need a running production host: TLS settings, Caddy's behaviour, the Docker image's runtime (the image's compose file has no `cap_drop`, `read_only` or `no-new-privileges`; hardening it is a LOW suggestion I did not make because I could not start Docker).
- Anyone with a verified Google account may sign in unless `WORKBUDDY_ALLOWED_EMAILS` is set (`docker-compose.yml` leaves it empty). That is a product decision, not an ASVS item; per-person rate limits, per-session quotas and the storage cap bound what such a person can use.
- The model provider receives the user's message and the uploaded file's name, never the file's contents (Brain's and Think's prompts). Outside ASVS.
- A turn that passes its deadline keeps its thread and CPU (`docs/backlog.md`, backend-api-core live runs); the number of running turns is capped, but a hostile file can still make a turn slow within the limits above.
