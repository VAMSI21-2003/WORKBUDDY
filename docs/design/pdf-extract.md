# The first PDF skill: take the one plain table of a PDF into a new spreadsheet

Branch `feat/pdf-extract`. Rule-touching (rule 1: a new verifier, and a reply that states what it measured; rule 2: a PDF is untrusted input read next to the user's original) and security code (a parser for untrusted files), so it goes through `docs/process/review-loop.md` with an Opus reviewer.

## What it does

A PDF with a text layer that holds **one plain table** becomes a new `.xlsx` under `workspace/outputs/`. The PDF is only read, as bytes. The spreadsheet holds **text only**: each cell is the words the PDF has in that cell. The reply says what was measured (rows and columns), says the cells are text, and carries the same "values only" sentence every copy carries.

"Plain" means a grid: every cell drawn with a border on all four sides, no cell running across two columns or two rows. That is what a ruled table looks like in a PDF's drawing commands, and it is what both parsers below can tell without guessing. Tables made only of aligned text (no rules) are out of scope: telling them from paragraphs is a judgement, and a wrong judgement would be a wrong table.

Refused, with a fixed sentence and no file (same style as the multi-sheet refusal; `skills/pdf/extract_table.py`, `REFUSALS`): no text layer (a scan; there is no OCR), more than one table (a table that runs over several pages counts as several), encrypted, not plain (merged or spanning cells, or cells that don't line up), no table found, a table of a single column (rules around the rows only: its columns aren't ruled), text that sits too close to a cell's border, or runs past it ("for me to be sure which cell it belongs to"), a table with columns that aren't ruled (two columns share one cell), more than 20 pages, too large (more than 50,000 cells, or a cell with more than 2,000 characters), unreadable or hostile, took too long, and "PDF reading isn't available on this server".

## Decisions

1. **Brain gets one closed action, `extract_pdf_table`** (`buddy/actions.py`, the single action table; `buddy/brain.py` prompt and intent vocabulary). It has no `mention` pattern, so the mention detector never adds or confirms it: only Brain's reading puts it in the ledger. `tests/buddy/test_pdf_extract.py` shows a message with the right words and a Brain reading of `unclear` runs nothing. No list of words anywhere decides what a request means; `Action.removes_rows` and `Action.extracts_table` are flags of the table's rows, not readings of a message.
2. **Write tier, not Read.** `docs/BUDDY_SKILLS.md` lists PDF text extraction as Read because it changes nothing. This skill hands back a new file, and Hands' chain, the verifier's step handling, the reply's "a file was changed" rules and the confirmation card all follow the tier: a Read-tier step is outside the chain, never counted as an action, and its output is "other output". Write is the tier of a skill that creates a file in the workspace, so the person is asked before it runs, like the row-cleaning skills. *Owner: say if you want Read.* It would need the outcome code to treat a Read-tier file-producing step as an action.
3. **Cells are text; nothing is converted.** The normal form of a cell is NFC (a letter and its accent are one character), the ligatures U+FB00..U+FB06 written as the letters, format characters and unassigned code points dropped, and whitespace folded. It is **not** NFKC (review round 1, H2): that turns `2½` into `21⁄2`, `m²` into `m2` and `™` into `TM`, which are other values. `007` stays `007`, `1,234.50` stays text, a cell reading `=SUM(A1)` is stored as that text (`data_type` is set to string after the value; a test reads the sheet's XML for any `<f>`). Converting would be a guess about the PDF's meaning (a date? a code?), and a wrong guess is a changed value. The reply says so in one fixed sentence (`TABLE_TEXT_SENTENCE`). The size is stated the way the cleaning replies count (review round 1, M1): "3 columns, a first row and 4 rows below it", so a later "removed 1 duplicate row, the copy has 3 rows" adds up.
4. **Two parsers, one answer.** The skill reads with pdfplumber (pdfminer.six). The Inspector's `PdfTableVerifier` reads the PDF again with PDFium (pypdfium2) and its own structure code (`skills/pdf/_worker/geometry.py`: ruling lines to grid, no pdfplumber code), reads the delivered `.xlsx` with openpyxl, and **fails the turn unless every cell matches**: the second reading finds exactly one table, it is a plain grid of two columns or more, and the text of its rows lays out cell by cell. Both readings clip a cell to its box the same way, so their agreement can't show a fault in that; `_text_layout_problem` looks at the characters themselves: no character sits beside the table on one of its rows or crosses a rule, no one string the PDF draws (one text object) has characters in two cells, and (review rounds 3 and 4, R3-H1 and R3-M1) **every line is rebuilt from the characters' positions, however the PDF split it into text objects**: characters are grouped into lines by their baselines and sorted left to right, and each pair of neighbours is judged by the gap between their advance boxes in ems (the font size). Neighbours in different cells closer than 0.5 em are refused as text too close to a border (a rule that falls in a word space puts the two halves of a sentence 0.20 to 0.28 em apart; the tight cells of a LibreOffice Writer table sit 0.30 to 0.35 em from their neighbours, which is why they are refused); neighbours in one cell further apart than 1.0 em are two columns without a rule (one space measures 0.28 em in Helvetica, also beside a dash or a tilde in the 16 punctuation cells tried; three spaces 0.83 em; the unruled columns of the review's table 2.2 em). The mechanism is the reviewer's prototype (`scripts/review_harness/feat-pdf-extract/r3_prototype_fix.diff`); its cost is that tables with tight auto-fit columns (LibreOffice Writer's) are refused, never mis-delivered, and no threshold between a word space and such a column is safe. The first version of this check grouped characters by guessed lines and was patched in two rounds (review round 1 H1, round 2 R2-H1); it was replaced by the object-identity rule, which round 3 showed covers one text object only; this is the second replacement, and it doesn't depend on how the PDF drew the text. the workbook has one sheet named `Table` with only text cells, nothing outside the table's size, and each cell equals the second reading's. A test runs both worker modes and checks which libraries each loaded. The reply's counts are the verifier's, not the skill's.
5. **A parser that is attacked can only end in a refusal** (the next section).
6. **Page cap at upload.** A `.pdf` upload is checked for `%PDF-` at byte 0 (not just the extension; an `.xlsx` with PDF bytes or the reverse is refused) and its pages are counted by the sandboxed worker (`probe` mode), so a refused upload leaves nothing behind. 20 pages or fewer is accepted; an encrypted PDF is accepted (its pages can't be counted, and the turn says it is encrypted). The worker checks the cap again on every read: a PDF can lie about its page count.
7. **The 2 MiB cap is shared** (`max_upload_bytes`); `.pdf` is added to the accepted extensions (`backend/settings.py`), the page's label and the error texts say so, and `backend/openapi.json` is regenerated.
8. **The row-cleaning skills no longer convert cells' types.** *Found while writing the follow-up test, and needed for it.* `pandas.read_excel` turns a column of text that looks like numbers into numbers: `007` became `7`, `2.50` became `2.5`, and a long account number becomes a float that has lost digits. For a workbook with text cells that was already true of "remove duplicate rows"; for a table taken out of a PDF, where every cell is text, it would happen on the first follow-up and nothing in the reply would say so. `dedupe.py`, `remove_empty_rows.py` and the Inspector's reads of their input and output now pass `dtype=object`, so a text cell stays text and a number stays a number, and the verifier can tell a skill that converts from one that doesn't. All existing tests pass unchanged. *This touches the existing skills; the reviewer should read it as part of the diff.*
9. **A request to extract a PDF's table reads the PDF, not the copy handed back from it.** After an extraction the session's "latest copy" of the upload is the extracted spreadsheet, and the follow-up default is to build on it (so "now remove the duplicates" works). A second "extract the table" would otherwise be planned against that spreadsheet, which no PDF skill can read, and end in "no available skill can do it". `Action.reads_upload` (true for the extraction) makes `choose_file` use the upload for a request Brain read as that action; the reply says the copy was not used (the existing "not on a copy I handed back earlier" sentence). It is Brain's closed reading (the ledger), not the message, that decides.
10. **Known limit, stated in the reply as a refusal:** "extract the table and then remove the duplicates" in one message does not start. Hands routes every step of a plan against the first step's input, and the cleaning skills can't read a PDF, so the chain is blocked before it runs (the existing "a chain that contains a step no skill can run doesn't start" rule) and the reply says nothing ran. The follow-up works as a second message on the delivered `.xlsx`. Making a chain carry a type change from the PDF to the sheet is a change to Hands' routing and is in the backlog.

## The sandbox

`skills/pdf/sandbox.py` starts `skills/pdf/_worker/main.py` as a separate Python process for every read of a PDF. The server never imports a PDF parser.

- **Wall-clock timeout**: 20 s; then the whole process group is killed and reaped.
- **Memory**: `RLIMIT_AS` 1 GiB, set by the worker on itself before it imports a parser (not through `preexec_fn`, which is unsafe in a threaded server). Also `RLIMIT_CPU` 30 s, `RLIMIT_FSIZE` 8 MiB (the answer is written to a file, so this caps it), 64 open files, no core dump.
- **No network, no programs, no new processes**: a seccomp-bpf filter (installed with `PR_SET_NO_NEW_PRIVS`, no privilege needed, x86-64 and arm64) makes `socket`, `socketpair`, the three `io_uring` calls (which can open sockets themselves), `execve`, `execveat`, `ptrace`, `process_vm_readv`/`writev`, `fork` and `vfork` fail with `EPERM`; `clone` is allowed only with `CLONE_THREAD` (a thread starts, a process doesn't) and `clone3` answers `ENOSYS` so libc falls back to `clone`; on x86-64 a call in the x32 numbering kills the process. `socket` is also unusable from Python. `python -m skills.pdf` runs the worker's `selftest` and exits 0 only if each was refused (and threads still work): run it where the server runs.
- **No handle on the server** (review rounds 2 and 3, R2-M3 and R3-M2): `pidfd_open`, `pidfd_getfd`, `pidfd_send_signal`, `tkill` and the queued-signal calls are refused, and `kill`/`tgkill` are allowed only on the worker's own pid, so a taken-over parser can neither signal the server nor take its connected sockets. The calls that change another process by its pid are allowed only on pid 0 or the worker's own pid (`prlimit64`, `sched_setparam`, `sched_setscheduler`, `sched_setaffinity`, `sched_setattr`, `migrate_pages`, `move_pages`) or refused (`setpriority`, `ioprio_set`): round 3 killed a server with `prlimit64` (a CPU limit of one second) and starved another of file descriptors. `selftest` tries every one of them on the server from inside the worker, and a test makes the real attempts from a worker whose parent is a throwaway server and checks nothing about it changed.
- **First to be stopped when memory runs out** (review round 3, decision 7): the worker sets its own `oom_score_adj` to 1000 (raising it needs no privilege) before the filter is installed, so the kernel's out-of-memory killer, in the container's 2 GB or on the host, stops a worker before the server. If the setting can't be made the worker parses nothing (it fails closed), and `selftest` reads back what the kernel holds.
- **No files beyond the Python installation** (review round 1, M4): after the parser modules are imported, a Landlock ruleset (Linux 5.13+, no privilege) lets the worker read only the Python prefix, site-packages and the system library directories, and write, create, truncate or delete nothing. It cannot read another person's upload or the server's environment (`/proc/<pid>/environ`) and cannot change a read-only upload's bytes. **Where Landlock is missing, the worker reads no PDF** (it fails closed; round 2 showed that without it the server's environment and sockets are within reach): uploads of PDFs are refused with "PDFs can't be read on this server right now", and `python -m skills.pdf` exits 1 and says why. *Owner: if the container's seccomp profile blocks `landlock_*`, either loosen the profile or accept that PDFs are off; there is no weaker mode.* The worker reads its memory peaks from a `/proc/self/status` descriptor opened before the ruleset.
- **Nothing handed over**: the worker gets the PDF's bytes on stdin, never a path; it runs with an empty environment (`env={}`, `-I`) in an empty temporary folder; its stderr is discarded.
- **Fails closed**: anywhere the filter can't be built (not Linux, an architecture the file has no numbers for, a runtime that refuses `prctl`), the worker parses nothing and the reply says PDFs can't be read on this server. On a Windows development machine the PDF tests are skipped and an uploaded PDF is refused.
- **Never follows anything**: neither parser executes JavaScript or follows a link, and the worker couldn't reach the network or start a program if one did. A test builds a PDF with an `/OpenAction` JavaScript that submits a form, a `/Launch`, a `/URI` link and an embedded file, listens on the port they name, and checks it hears nothing, nothing is written, and the table is read.
- **Bounded**: one worker runs at a time in the server (another waits up to 15 s, then is refused as busy), so the memory in use at once is one limit, not one per concurrent turn. It was two until round 3: a dense PDF measured 706 MiB resident, two such workers and the server don't fit the app container (now 2 GB, `deploy/docker-compose.yml`).
- **The worker's answer is untrusted too**: parsed strictly; a status or reason outside a closed set is `bad_output`; cells are re-validated (rectangular, strings in normal form, within the size limits) before anything is written. Reasons are codes, and the sentence for each is fixed text in the parent: no word read from a PDF and no exception's text reaches a reply.

Libraries are pinned with hashes in both lock files (additions only: `pdfminer-six`, `pdfplumber`, `pypdfium2`, and `reportlab` in the dev lock for the tests; Pillow and cryptography were already pinned). No system package was needed to build and test this (the PDFium library ships inside the `pypdfium2` wheel, and reading text needs no font), so no package was added to the image. `deploy/` changed in round 4: the app's memory limit is 2 GB (one worker at a time). The Dockerfile's pip step retries a failed download (`--retries 10 --timeout 60`). The sandbox was checked inside the production image on the owner's VM at `1575f04` (`python -m skills.pdf`: every check true, Landlock works under its Docker), and CI now runs the same command in the built image and requires "The PDF sandbox holds.".

## What it does not do (backlog)

A table whose columns aren't ruled but whose rows are (refused: one column, or two columns in one cell); tables of aligned text with no rules; a report requested together with the extraction (the analysis is not planned on a PDF, so the table is handed back and the reply says no report was made); a table that continues over several pages (counted as several); choosing which table or pages; scanned PDFs (OCR); typed cells (numbers, dates); a chain from the PDF to a cleaning step in one message; merged cells; password-protected PDFs.

`tests/skills/pdf/` (the pure modules; the sandbox's limits with real misbehaving processes; the skill on real PDFs; hostile PDFs: a 200,000-deep nested array, a page tree 20,000 levels deep and one that contains itself, 25,000 pages, a page count that lies, a 1.5 GiB compression bomb in 1.5 MB, wrong/missing/huge/looping xref tables, garbage), `tests/buddy/test_pdf_extract.py` (the whole pipeline in all three speakers; the verifier's every failure; a skill that lies is stopped), `tests/backend/test_pdf_turns.py` (upload, extract, then "now remove the duplicate rows" on the delivered sheet, file settling by name, start over).
